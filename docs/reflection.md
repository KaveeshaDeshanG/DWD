# Reflection

Community Sports Facilities Booking System — coursework reflection. Written from the actual, real development history of this repository (git log, `docs/traceability-matrix.md`, `docs/marking-scheme-checklist.md`, and the test suite), not a template. Nothing here is speculative evidence — where something cannot be verified from the repository itself, it is named as such rather than assumed.

## 1. System Overview

A Community Sports Facilities Booking System built as an ASP.NET Core MVC (.NET 10) application over SQL Server, using Entity Framework Core as a thin, hand-mapped data-access layer (no `EnsureCreated()`, no EF migrations — the SQL scripts under `database/` are the single source of schema truth, matching the project constitution's Principle VI). It supports two actor types: **Guests** (unauthenticated visitors who can browse facilities, run a restricted search, read reviews, register, and submit an inquiry) and **Members** (registered users who can additionally search with date/time availability, book facilities, view their booking history, submit reviews for completed bookings, and manage their profile and preferred sports).

## 2. Requirements

Requirements were captured incrementally through a SpecKit-based workflow (`specs/001-mvc-foundation`, `specs/002-member-functionality`, `specs/003-facility-search-booking`, plus the flat `specs/SPEC-001..019` set from the initial requirements/design phase) rather than written once and left static. Each feature phase produced a `spec.md` (user stories, functional requirements, acceptance scenarios) before any code was written, and `docs/traceability-matrix.md` maps every requirement to its specification, database component, MVC component, and test evidence.

## 3. Architecture

- **Custom authentication**, not ASP.NET Core Identity: a `Member` table + `PasswordHasher<Member>` + cookie authentication. This was a deliberate trade-off, not an oversight — Identity's own `AspNetUsers`/`AspNetRoles`/claims tables would have added framework-owned tables to the ER diagram and data dictionary (the coursework's largest single mark pool) that the student did not design, in exchange for features (external logins, lockout policies, 2FA) the brief never asked for.
- **Booking concurrency** is a genuine three-layer defense, not a single check: an application-level pre-check for fast user feedback, a `sp_getapplock`-guarded transaction inside `usp_CreateBooking` that actually closes the race, and an `AFTER INSERT, UPDATE` trigger (`trg_Booking_PreventOverlap`) as a database-level backstop that fires regardless of which code path wrote the row. This exists because SQL Server has no native exclusion constraint for arbitrary time ranges (unlike PostgreSQL's `EXCLUDE USING gist`).
- **Static services, not DI-registered classes**, for pure cross-cutting logic shared by more than one controller (`FacilityAvailabilityService`, `BookingService`, `SportsPreferenceService`, `ReviewService`, `ImageResolver`). This kept `Program.cs` free of incidental registration churn as each feature phase landed.
- **Ownership is structural, not a checked condition, wherever the architecture allows it**: `ProfileController` and `BookingController.MyBookings` never accept a member identifier from the client at all — they resolve it from the authentication claim (`ClaimsPrincipalExtensions.GetMemberId()`) and query only that member's own rows. `ReviewController.Create` is the one place a client-supplied identifier (`BookingId`) is unavoidable, since a review must reference a specific existing booking; there, ownership is re-verified from the claim on every request (GET and POST independently) rather than trusted from a hidden field, and a mismatch returns `NotFound` rather than `Forbid` so a probing request can't distinguish "doesn't exist" from "isn't yours."

## 4. Database Design

Eight tables (`Member`, `Sport`, `MemberSport`, `Facility`, `FacilitySport`, `Booking`, `Review`, `Inquiry`), normalized to 3NF. Two design decisions are worth calling out because they were reached through actual normalization analysis rather than copied from a template:
- `Review.BookingId` is both the primary key and the foreign key to `Booking` — a 1:0..1 identifying relationship that enforces "at most one review per booking" through the primary key itself, with no extra `UNIQUE` constraint needed.
- `Review` stores neither `MemberId` nor `FacilityId` directly, even though the original design draft had them — both are reachable via `Review → Booking → Member`/`Facility`, and storing them redundantly would have been a transitive (non-3NF) dependency.

`MemberSport`/`FacilitySport` are pure composite-primary-key associative entities with no surrogate key, which is also what makes duplicate preference/support rows structurally impossible rather than merely validated against.

## 5. SQL Implementation

`database/01_CreateDatabase.sql` through `06_TestQueries.sql` were not just written but actually executed against a real local SQL Server instance during development, and re-run as the schema evolved (most recently, extending the `Sport` catalog with Cricket and Volleyball and renaming the "Football" entry to "Soccer" to match the coursework brief's own terminology — an `UPDATE`/idempotent `INSERT` applied directly to the live database and mirrored into the seed script, not a destructive re-seed, so existing `Booking`/`Review`/`MemberSport` rows and their IDs were never disturbed). `06_TestQueries.sql` contains ten non-trivial `SELECT` queries (joins, aggregates, `EXISTS`-based availability checks) — no bare `SELECT *` anywhere.

## 6. MVC Implementation

Built in phases (MVC Foundation → Member Functionality → Facility Search & Booking → this audit's Review/Inquiry/Cricket-Volleyball/UI pass), each phase live-tested against the running application and real database before being considered done. The single biggest late addition was **Review submission and Guest review search, and the Inquiry contact form** — these had database tables and EF Core mappings in place since the original database-implementation phase, but no controller or view existed until this audit identified the gap against the marking scheme and built `ReviewController`/`InquiryController` and their views, reusing the existing design system (`.form-card`, `.page-section`, validation-summary styling, Bootstrap Icons) rather than introducing new visual patterns.

## 7. Testing

Every test class runs against the real `CommunitySportsBookingDB`, not an in-memory provider or mocks — a deliberate constitution principle, on the reasoning that an in-memory EF Core provider silently accepts things (like a violated `CHECK` constraint) that the real SQL Server schema would reject, which would make a passing test suite lie about database-level correctness. The cost of that choice was real: xUnit parallelizes test *classes* by default, and because every class touches the same live database, two classes running concurrently could observe each other's in-flight rows — fixed with a shared `[CollectionDefinition("Database collection")]` forcing sequential execution, not by weakening any assertion.

## 8. Security

- Passwords are never stored or compared as plaintext — `PasswordHasher<Member>` (PBKDF2) throughout, verified by an actual test that the stored hash is not the original password and round-trips correctly.
- Every state-changing POST action carries `[ValidateAntiForgeryToken]`.
- View models are deliberately narrow to prevent overposting: `CreateBookingViewModel`, `ProfileEditViewModel`, and `CreateReviewViewModel` have no `MemberId`/`FacilityId` property at all, so there is no request shape that could target another member's data even if a client crafted one.
- Login failures are generic ("Invalid email or password") regardless of whether the email or the password was wrong, and `ReviewController`'s ownership check returns `NotFound` rather than `Forbid` for the same information-disclosure reason.
- Guest-restricted search (`FacilityController.Search`) strips Date/Time parameters from an unauthenticated request server-side before validation runs, not merely by hiding the fields in the view — a crafted POST from a Guest cannot obtain availability data.

## 9. Validation

Server-side `DataAnnotations` on every ViewModel (`[Required]`, `[EmailAddress]`, `[StringLength]`, `[Range]`, `[RegularExpression]`), enforced again at the database layer by `CHECK`/`UNIQUE` constraints as the authoritative backstop — proven directly by a test (`Registration_DuplicateEmail_RejectedByDatabaseConstraint`) that bypasses the controller's own pre-check to confirm the database itself refuses a duplicate email.

## 10. Challenges Encountered and Solutions

These are real bugs caught during development, not hypothetical risks — each one was found by actually running the application or its tests, not by reading the code and guessing:

1. **Conventional routing swallowing an ID as an action name.** `GET /Facility/1` 404'd because the app's `{controller}/{action}/{id?}` route read "1" as an action name. Fixed with an explicit `[HttpGet("Facility/{id:int}")]` attribute route on `Details` only.
2. **A route-parameter name mismatch silently zeroing every error page's HTTP status.** `HomeController.StatusCode(int code)` never received a value because the route key is `id`, not `code` — `Response.StatusCode` silently became `0`, producing a malformed HTTP status line that broke real HTTP clients. Only caught by a raw socket read, not by `dotnet build` or a normal browser request. Renamed to `StatusCodePage(int id)` with `[ActionName("StatusCode")]`.
3. **A malformed SVG that silently failed to render.** `badminton.svg` had two `stroke` attributes on the same element — invalid XML, which a browser's `<img>` SVG parser rejects outright (no error, just a blank image). Caught by actually validating every icon file's XML well-formedness with a real parser, not by eyeballing the markup; the same validation step is now applied to every new icon (Cricket, Volleyball) before it ships.
4. **Test-suite flakiness from parallel access to one shared database** (§7 above).
5. **An uncommitted "done" phase drifting silently.** A prior session's memory recorded Phase 7 as "fully done and verified," but further edits happened on top of it with no git commit as a checkpoint, and a later session found the build actually broken. The working rule since: never trust a "verified" claim for anything not yet committed — re-run the build/tests before relying on it.
6. **Two entire marking-scheme features (Review submission, Inquiry) had their database tables and EF mappings ready from early on but no web-layer code**, discovered only by explicitly auditing the marking scheme line-by-line against the actual controller list rather than assuming "the database is done" meant "the feature is done."
7. **EF Core's default generated SQL is incompatible with a table that has a trigger.** The very first direct EF Core insert into `Booking` ever written (a test helper for the new Review tests) failed with `DbUpdateException`: SQL Server refuses `INSERT ... OUTPUT INSERTED.*` on a table with an enabled trigger, and `trg_Booking_PreventOverlap` makes `Booking` exactly that. The application itself never hit this because real booking creation goes through `usp_CreateBooking` via raw SQL, bypassing EF's change tracker entirely — but the mapping was still latently wrong for any future direct EF write. Fixed once, at the mapping level (`BookingConfiguration.ToTable("Booking", tb => tb.UseSqlOutputClause(false))`), rather than only worked around in the test.
8. **A locked build during this very audit.** Visual Studio had the solution open (and the app running under its debugger) while this session needed to build and test — `dotnet build`/`dotnet test` failed with a file-lock error pointing at `devenv.exe`. The correct response was not to force-kill the user's IDE, but to redirect the build output to an isolated directory (`dotnet build --output <scratch dir>`) — same source, same compiler, zero risk to the user's own session, and it produced real, trustworthy build/test/HTTP evidence without needing Visual Studio to let go of anything.
9. **The facility search filter silently returned zero results for most sports.** Found by actually running a search for each of the 8 sports rather than trusting that "Cricket and Volleyball are linked via FacilitySport" meant "searching for them works." The `FacilityType` search field only ever matched `Facility.FacilityType` text (e.g. "Sports Hall"), never the sport a facility supports via `FacilitySport` — so clicking the Home page's Basketball tile (which links to `/Facility/Search?facilityType=Basketball`) and searching returned nothing, because no facility's `FacilityType` literally contains the word "Basketball". The same gap silently affected Soccer ("Football Pitch"), Cricket, and Volleyball — 4 of 8 sports had a broken tile-to-results path. Fixed by matching either the facility's own type text or a sport it supports, an additive `OR` that changes no existing passing search and required updating one test whose old expectation (`Assert.Empty`) had encoded the bug rather than the intended behavior.
10. **Two facility-count assumptions in already-existing tests went stale** when this session added two new active facilities (Eastfield Cricket Ground, Southgate Volleyball Court) for Cricket and Volleyball specifically, rather than leaving them only loosely associated with unrelated existing venues. `Search_EmptyFilters_ReturnsAllActiveFacilities` (hardcoded 5 active facilities) and `ImageResolverTests`' "unknown facility type" example (which had used "Cricket Ground" — true when written, false the moment a real mapping for it was added) both needed updating to the new, correct baseline.

## 11. Future Improvements

Honestly out of scope for this coursework but worth naming for a real deployment:
- A `BookingStatus` column and member-initiated cancellation (deliberately omitted now — with no cancellation feature, a status column would only ever hold one constant value).
- Email notifications for booking confirmation and inquiry responses.
- An admin/facility-management role — the brief's own case-study narrative gestures at facility-management oversight, but the marking scheme defines only Guest and Member actors, so this was treated as explicitly out of scope rather than built speculatively.
- Pagination on the Review/Facility search result lists, which currently return their full result set (fine at this data volume, not a pattern that scales indefinitely).

## 12. Known Limitations (stated plainly, not hidden)

- **The ER diagram and the SQL Developer Data Modeler physical model (25 of the 30 Database Specification marks) require a human to actually build them in the Oracle SQL Developer Data Modeler desktop application.** `docs/data-modeler-guide.md` gives the exact entity/attribute/relationship spec and step-by-step build instructions cross-checked against the real schema, but no screenshot, exported DDL preview, or `.dmd` file exists in this repository as of this writing. This is stated here explicitly rather than implied to exist — see `docs/marking-scheme-checklist.md` for the same status tracked line-by-line.
- Automated tests run against a real local SQL Server instance rather than a portable test container, so `dotnet test` in a different environment without that instance configured will fail to connect — this is a deliberate trade-off (§7) but does mean the test suite is not maintainer-portable out of the box.
- UI/responsive verification in this project's assistant-driven sessions has been done via real HTTP requests (status codes, response headers, rendered markup, cookie behavior) and static analysis (SVG XML validation, CSS brace-balance, JS syntax checks), not actual browser screenshots at multiple viewport widths — no browser automation tool has been available in that environment. A manual pass in a real browser at desktop/tablet/mobile widths is recommended before submission.
